## 内存扫描

- **游戏更新后地址会静默失效**：exe 换了，脚本照跑不报错，只是读到垃圾 ——
  自机不动、往弹幕里走，或画面被判成非关卡而**拒绝发键**（表现为「脚本用不了」）。
  原因：全局变量 RVA 只对某个构建有效。2026-09-24 Steam 更新（MD5
  `b0cc28ec…` → `fe47d9c2…`）就是这么让整套避弹报废的。
  **别手工改地址：跑 `py tools\autofix.py`** —— 按反汇编特征重新定位，写
  `tools/addr_cache.json`，源码一行不用动（`tools/addr.py` 在 import 时套用）。
  launcher 检测到构建变了会自动跑它。
  依据：**结构内偏移 / 池 stride / 槽数从来不随更新变**，变的只有全局变量位置。

- **全内存浮点扫描吃 5GB 内存**：值域设 [-50, 1200] 时命中 1.52 亿个 float，Python 进程涨到 5.3GB 后被中止。
  原因：683MB 里绝大多数是图形/音频缓冲，宽值域下几乎全命中。
  **只扫 ≤4MB 的小块区域；值域按已知坐标范围收紧到 x∈[0,384]、y∈[0,448]。**

- **按 stride 盲扫找不到子弹池**：连续数轮扫描，命中全部落在图形数据或归一化浮点区。
  原因：没有基址时采样窗口会跨过图形缓冲，且图形数据里小浮点极多，噪声淹没信号。
  **先反汇编拿"结构 + 基址来源"，再写针对性验证；别用扫描代替反汇编。**

- **"变化最密集的内存页"不等于游戏逻辑**：三个 2MB 页变化量完全相同，实为三重渲染目标。
  原因：渲染缓冲每帧全量改写。
  **排除镜像副本（多页变化量完全相同即为渲染目标）。**

- **`0x4F27B9` 恒为 0**：游戏正常生成弹幕时它仍是 0，容易误判成"游戏没在跑"。
  原因：该地址不是运行判据，此前把它命名为 NativeTime 有误。
  **别用它判断暂停/运行；改用子弹数变化或 Scene。**

- **别把参考项目的 `LEA RDX,[RCX+0x4C]` 当数组起点**：`0x4C` = 子弹数组偏移 `+8` + 槽内字段 `+0x44`。
  原因：编译器把 `&bullets[i].field` 折叠成一个常量偏移。
  **反推数组起点时先减去已知数组偏移，再用 stride 校验。**

- **别按原版偏移推算新典的结构**：拿 `ref-th06-decomp` 的 `GameManager` 偏移去找 `livesRemaining` / `isInRetryMenu`，候选地址读出来全是 0 或垃圾（`deaths=1574`）。
  原因：新典把游戏状态**拆成了独立全局**（Lives@`0x4FF0F0`、画面判据@`0x4FF0F2` …），x64 下布局也已重构。
  **先在代码里找引用（`tools/scan_globals.py`）→ 再用运行时值验证；别从原版结构表硬套。**

- **`0xC21D94` 不是帧计数**：当成 `Supervisor.calcCount` 用来判"游戏是否在跑"，实测变化次数 **0**，会永远判否。
  原因：它根本不被任何代码 RIP 引用（采集清单里没有它）。
  **帧计数是 `0xC21C00`（每帧 +1，0.27s 增 16）。**

- **最小化 ≠ 暂停**：窗口最小化时帧计数仍在走，游戏逻辑照常推进（Continue 倒计时也在走）。
  **判"游戏是否在跑"只能看帧计数，不能看窗口状态。**

- **反汇编不开 `skipdata` 只覆盖 1.4% 的 .text**：`.text` 里嵌着跳转表数据，
  裸 `md.disasm()` 碰到第一段无法解码的字节就**整体停止迭代**（实测停在 RVA `0xB5D0`），
  引用索引只建出 369 条，于是所有标量都显示"无人引用"，极易误判成
  「标量静态定不了，只能开游戏读值」。
  **建 md 时一律 `md.skipdata = True`**（`relocate.py` 的 main 早就设了，自己写诊断脚本时最容易漏）。

- **位移是分段的，不是全局一个值**：同一次更新里 `+0x43260`（Player 段）、
  `+0x4AC50`（子弹/状态变量段）、`+0x4C220`（输入/道具段）并存，相邻变量可能分属不同档。
  用「单一参考位移 + 大容差」筛候选会把无关变量一起放进来。
  **先由特征锚点标定出位移档，再用「档位 + 必须被代码引用」双重约束推其余地址**（`autofix.py` 的做法）。

- **「引用数最多」不能当选址判据**：`g_EnemyManager` 正确答案只有 2 处引用、
  邻居却有 6 处；子弹池基址一度被引到 `0x5542B0`（被引用 54 次的热门全局）。
  **判据是「位移档 + 锚点邻域确实访问了槽内字段 + 信噪比」，引用数只用来在同档候选里排队。**

- **做读值验证前必须确认游戏真的在推进**：拿一个**已确认的**帧计数读两次看是否增长，
  否则读到的是暂停快照 —— `LIVES` 读成 0 看着像地址定位错了，其实可能只是游戏没跑。
  ⚠ 反过来也错：**窗口不在前台 ≠ 暂停**（实测前台是别的程序时帧计数照走 60/秒），
  别用窗口状态推断暂停，只能看帧计数本身。

- **`inc byte [rip+X]` 不足以认定帧计数**：新构建里 `0xC6DFD6` / `0xC6DFD7` 是一对相邻的
  动画计数器，各自都有完整的 `inc` + `dec` + `cmp ...,9` 形态、被引用 9 / 7 处 ——
  形态上就是教科书式的帧计数，**实测却一秒都不涨**；真正的帧计数 `0xC6DE20`
  反而只有 **1 处** rip 引用（其余访问走寄存器间接，索引抓不到）。
  **帧计数只能按速率认**（60fps 下约 60/秒），`autofix.pick_frame_counter()` 就是这么做的。
  推广：**「形态最典型」和「引用数最多」都不是选址判据** —— 同一轮里 `g_EnemyManager`
  正确答案只有 2 处引用、邻居有 6 处；子弹池曾被引到被引用 54 次的热门全局。

- **「形态完整的 switch 变量」也不是 curState**：新构建里 `0xC6DFC0` 有教科书式的
  12 分支跳转表分派（`movsxd rax,[rip+X]` + `cmp eax,0xb` + `ja` + `jmp reg`），
  **却只有 1 处引用、从不被赋值** —— 它更像关卡号（关卡内恰为 1）。
  真正的 curState `0xC6DFBC` 被赋 `1/7/8/0xc` 四个不同场景号、47 处引用。
  错 4 字节的后果是**关卡内判成 MENU、脚本拒绝启动**（用户直接看到的就是这个）。
  **判据是「被反复赋予不同的场景号」+ 引用数**，不是 switch 形态。
  ⚠ 定位完必须过一遍运行时 `curState == wantedState` —— 二者相邻且通常相等，
  **不等就说明至少有一个地址错位**，这条行为判据比任何静态指纹都硬。

- **「值落在场地内」不足以认定自机坐标**：错档地址 `0x549D30` 上放着**场地矩形常量**
  `{8, 16, 368, 416}`（= 左 / 上 / 宽 / 高），两个值都落在场地内、看着完全合理，
  却连续几秒一字不变。把 `实读 8.0 / 16.0` 当成"合理值"收下 → **坐标整档错位**，
  避弹读到假位置，表现是"能启动但完全不能正常用"。
  **坐标的判据是 `PLAYER_X + 0x1C`（判定半径）实读 `1.25`** —— 基址错档时这里读 `0.00`。
  再配两条交叉验证：`PLAYER_HITBOX = PLAYER_X + 0x1C`、`LIVES = PLAYER_BASE − 0x2B0`。
  ⚠ **读值判据别放宽**：`0.0 <= hitbox <= 8.0`、`0 <= x <= 512` 这类宽区间会让错误地址
  **假通过** —— 判据放宽本身就是漏检的来源，比没有判据更危险（它给的是"已验证"的错觉）。

- **池基址的锚点是「遍历起点」，不是结构基址**：`relocate` 用 `add rbx,0x10B0` 找敌人池，
  它 `lea` 到的是 `enemies[0]`（= `g_EnemyManager + ENEMIES_OFF(8)`）。照抄这个值当
  `EM_RVA`，调用方再加 8 就**每槽整体错位** —— 占用标志全读成 0，表现是「敌 0」，
  于是 `pick_target()` 恒返回 `None`、**进攻权重调多大都是 0**。
  ⚠ 最阴的是：错位后照样能捞到几个「看着像坐标」的 float，而**验证代码如果也没加
  `ENEMIES_OFF`，两个错误正好抵消、检查反而报「✓ 敌人落在场地内」**。
  判据要用**占用标志**（`flags1 & 0x80`），不是「坐标落在场地内」。
  同理记住 `BULLETS_OFF` / `ENEMIES_OFF` 都是 `0x8`，凡是读池都要带上。

## 游戏交互

- **暂停时方向键无效**：自机纹丝不动，容易误判为"SendInput 失败"。
  原因：暂停冻结游戏逻辑。
  **发移动键前先按 `Z` 解除暂停（暂停菜单默认高亮「解除暂停」）。**

- **按键打进别的程序**：QQ / 浏览器抢到前台时，SendInput 的字母键变成打字。
  原因：`GetAsyncKeyState` 是全局键状态，游戏失焦也读得到，但前台窗口同样收得到。
  **发字母键前用 `find_windows` 校验前台 hwnd；不确定时只发方向键。**

- **`SetWindowPos` 改窗口模式无效**：返回 True 但尺寸被改回全屏。
  原因：游戏每帧重设窗口尺寸。
  **不要依赖强制改窗口；截图直接截全屏（1920×1080）。**

- **被中止的命令会改变游戏状态**：工具调用中断后，暂停态/自机位置可能已变。
  **每次操作前先用 `py tools\check.py` 确认 Scene 与坐标。**

- **失焦会自动暂停，而脚本结束又把焦点还给了原窗口**：下次实跑若不先按 Z，自机纹丝不动，容易误判成"按键失效"。
  判据：读输入位图 `0xA6EC60`，按住方向时它会变（`0x80` = right、`0x10` = up），说明按键已送达游戏。
  **`tools/dodge.py` 默认开场按一次 Z**（游戏中 Z 只是射击，无害）。

- **自动射击别用反复 tap**：输出零零散散，射速上不去；每帧重复 `key_down` 还会让退出路径漏松键。
  原因：射击靠**按住状态**连射，`tap('z', 60)` 只按下约 4 帧。
  **`key_down('z')` 保持，只在状态变化时发一次；松键统一走 `run_session` 的 `finally`**（`dodge.apply_fire()`）。

- **在弹幕里抢前台做「按键验证」**：自机不动也照样被下一波弹幕收走 —— 验证的代价是一条命。
  原因：切前台发键期间脚本不避弹，弹幕不会因为你在做验证就停下。
  **先查「自机旁边有没有子弹」，近了就拒绝执行**（`tools/verify_focus.py` 的 `--near`，默认 60px）；
  挑关卡开头的飞行段 / 对话时跑。

- **"弹 0"不等于安全**：Stage 1 开场两次掉命都发生在子弹池为空时 —— 撞敌机 / 中激光。
  原因：目前只读 `bullets`，敌人本体与激光都不在其中。
  **别把"无弹"当作安全；躲避要纳入敌人本体与激光。**

- **别把激光的"预警线"当成已经打得到人的激光**：预警线本身没有伤害判定，
  拿它当实弹喂给必死预判，就会在激光还没释放时先白扔一颗炸弹。
  原因：激光池里 `state != 0` 只说明"活跃"，活跃 ≠ 有判定 —— 决定打不打得到人的是阶段字节
  `+0x290`，只有 `1`（发射）会调 `Player__CalcLaserHitbox`
  （依据 → `02-内存布局/相关-游戏内存映射-MEMMAP.md` §7.2）。
  **必死预判只喂 `flags == 1` 的激光**（`read_frame()` 的 `laser_armed`）；躲避仍看全部阶段 ——
  预警线就是马上要开火的位置，必须让开。

- **掉命瞬间脚本继续发键会点掉「续关」**：`Lives=0` 一死就进 Continue 画面（截图实证：「要续关吗？剩余 N 次 / 是 / 否」，**上下排列**），脚本发的方向键把「是」拨到「否」，这局直接作废。
  原因：**Continue 画面期间 `Scene` 仍读到 2**（实测连续 24 帧为 2，第 25 帧才变 7）；`--unpause` 又会在任意画面无条件按一次 Z。
  **判「能不能发键」的判据是 Continue 标志 `0x4FF0F2 == 0xFF`，不是 `Lives > 0`** —— 拿残机数当闸的代价是最后一条命站桩送死（旧版就这么错了）。脚本改在**死亡结算完**（`dying` 且 `respawn <= 0`）就松键退出，赶在 Continue 出现之前。

- **`start_game.py` 跑完游戏留在前台自动跑**：结束后焦点不回退，游戏**无人操作地继续运行**；Stage 1 开场杂兵会把不动的自机打死 3 次，直接送进 Continue 画面。
  原因：**只有失焦才自动暂停**，前台无人操作时游戏照常跑；`start_game.py` 收尾没恢复原前台窗口。
  **脚本结束立刻抢回焦点或暂停游戏；跑验证前先读 `Lives`，`Lives=0` 说明已经死光。**

- **Scene 不能判断当前在哪个菜单**：标题、难度、角色、御札选择全是 `Scene=1`。
  **只有 `2`（关卡中）与 `7`（Game Over 结算）可用于程序判态。**

- **难度菜单按键间隔要 ≥0.3s**：间隔 0.12s 时 up/down 会丢键，本想选 LUNATIC 却落在 HARD。
  **菜单导航用 `tap(key, 50)` + `sleep(0.3)`。**

- **按住 Z 推不动关卡开场的对话**：打穿一关进下一关后，脚本卡在第一句对话上不动（自机还能动，
  但关卡时间线停在对话里，永远不出敌人）。
  原因：对话的 `MSG_OPCODE_WAIT` 只认**按下沿**（原版 `Gui.cpp:577` `WAS_PRESSED(TH_BUTTON_SHOOT)`），
  两次按下沿还要隔 ≥8 帧 —— 自动射击是**按住** Z，按住状态永远不满足。
  **场上没有威胁源时周期性轻点 Z**（`StageFlow.tap_due`，默认 0.6s 一次）；
  **有威胁源时绝不轻点** —— 那会先松开正在连射的 Z。

- **别把 `curState=3` 当「未知场景」退出**：`SCENE_3`（GAMEMANAGER_REINIT）是**关卡之间的过渡态**，
  游戏自己会 `currentStage++` 并把下一关载入 —— 脚本在这里退出，就等于「打完一关就停」。
  原因：旧 `screen_of()` 只把 curState=2 当关卡，其余一律 `ok=False` 让主循环退出。
  **判为 `STAGE_SWITCH`：不退出、不按键地等过去**；超 `ADVANCE_TIMEOUT_S`(120s) 才算卡死。

- **Continue 画面与关卡过渡里都别做「预备接管」**：开场的预备接班会先按住一个方向键，
  在 Continue 画面上那就是把「是」拨到「否」（PITFALLS 上一条的扩大版）。
  **预备接管只在 `code == 'IN_GAME'` 时做**；`STAGE_SWITCH` 期间连开场的 Z 也不按。

- **`isInRetryMenu=0xFF` 不止「Continue 画面」一种**：符卡练习（Spell Practice）失败后的
  "Failed..." 菜单（返回符卡选择 / 保存Replay / **重试**）**同样是 0xFF**。
  现象：练符卡时被打中一次，脚本判 `CONTINUE` 退出 → 游戏重开符卡后自机静止 → 之后一路死。
  依据：`Player__OnUpdate` 的 `mov byte [0x549D42], 0xff`（RVA 0x6A430 = 原版 `Player.cpp:247`），
  自机一死就置位 —— 新典把这一位复用给了符卡失败菜单。
  **判 `CONTINUE`（= 失败菜单）时只松键不按方向键；要自动继续就开「失败菜单按 Z 继续」
  （符卡练习下光标默认在「重试」上，按 Z = 重开这张符卡；普通关卡下那是续关）。**

- **别把 `curState` 0 / 12 当「未知场景」退出**：按 Z 重开一张符卡依次经过 `12 → 0 → 2`，
  各只持续 1~2 帧。判未知场景 = 每重试一次就退出一次。
  原因：原版枚举只到 10，**12 是新典自加的**；0（INIT）虽原版就有，但同样是重载中间态。
  **两者都判 `RELOAD`：不退出、不按键地等**（超 `RELOAD_TIMEOUT` 才算卡死）。
  教训：补完 12 就以为完事，**同一局紧接着又死在 0 上** —— 过渡态要一次找齐。

- **别拿 CLI 跑出来的现象去解释控制台里的表现 —— 两者默认参数是两套**：
  命令行**不读** `dodge_params.json`（`SAVED_PATH` 只有 GUI 读），
  `--xxx` 的默认值全部取自 `dodge.default_params()`。
  现象：用 CLI 复现「贴墙 / 全程低速」并写进结论，而用户在控制台里跑的其实是另一套
  （`focus` 关着、`edge` 1000 而非 24、`clear` 100 而非 25、`attack` 0 而非 30 …… 几乎每项都不同），
  结论直接对不上。
  **要两边一致：把值写进 `default_params()`**（那才是唯一真源，GUI 控件与 CLI 默认值都从它来）。
  要复现用户的现场，先 `py -c "import sys;sys.path.insert(0,'tools');import dodge,json;
  print(json.dumps(dodge.default_params()))"` 与 `dodge_params.json` 对一遍。

- **「最优间隙」只算当前活跃弹，别拿它当「稳不稳」**：Laevatein 符卡 7 次死亡全在场地左侧
  （x=24~81），且全程 `⇩低速`。间隙看着有 38px，实际是竖直光柱**在自机位置上开火**。
  成因：该符卡的光柱**瞄准自机生成**（死亡现场里光柱 x 与自机 x 差 < 7px，且 `轴移=0 / 转角=0`），
  而预警线只进软项、不进安全分 → 低速判据误判「宽裕」→ 半速跑不出光柱半宽（12px）+ 自机半径。
  **看现场用 `py tools\watch_live.py`**：只读、不按键，打「谁碰上了」+ 激光完整参数 + 间隙曲线。

## 躲避决策

- **`None` 兼表「没给这个参数」与「给了，但它没有」→ 改进静默失效**：给 `plan()` 加
  `laser_armed`（安全分只认已开火的激光）时拿 `None` 表示「回落旧行为」，而 `read_frame`
  在**当前没有已开火激光**时也返回 `None` → 又回落到全阶段激光，改进恰好**在最需要它的
  那一刻**（激光还没开火）失效：改前改后分数逐字相同，看不出错。
  **判断**：「未提供」与「提供了空值」是两回事时用模块级哨兵（`dodge._AUTO`），别用 `None`。

- **`default_params()` 的 `attack` 是权重，`plan(attack=…)` 是坐标**：按 cfg 的键名传
  `params={'attack': 55}` 会把坐标覆盖成 float，`attack_cost()` 取下标时崩在
  `TypeError: 'float' object is not subscriptable`。**覆盖攻击吸引用 `attack_w`**。

- **`plan()` 的参数默认值别写成签名默认值**：`def plan(..., laser_margin=LASER_MARGIN)`
  在**定义时**求值，于是 monkey-patch `LASER_MARGIN` 的用例全部失效
  （`check_plan` 的「激光余量」那组当场红）。**写成 `=None`、在函数体内取常量**。

- **判「九向全负」时先问一句：是安全分真的都在圈里，还是余量把它压负的**：
  `LASER_MARGIN=16` 在 48 条激光上叠加时，每条对**九个方向同等**扣分 ——
  此时调余量（16→0）只是把整列分数平移，**排序逐字不变**，
  而 `pool` 的 `max(top - risk, 0.0)` 下限才是让软项整条旁路的那个闸门。

- **命中自机的弹**在命中那一帧**就转入消散**，被 `BULLET_SKIP_DESPAWN` 滤掉：取证工具若直接用
  `read_frame` 的 `bf`，判定帧上真凶**凭空消失**，严格几何判定只会说「没相交」。
  **取证读 `bf_raw`（未过滤整池，`read_frame` 已一并返回）**；
  已有数据用 `death_report.hit_ahead()`：拿上一帧的弹道外推一帧，落点正是命中位置。

- **取证复算走 `plan()` 的函数默认值 → 报出的「脚本视角」不是脚本当时算的分数**：
  `replan()` 原先只传世界派生量，`comfort / edge_w / attack_w / clear_w` 全落进 `plan()` 的兜底值；
  而实机跑的是 `dodge_params.json` 那套（实测差出 horizon 20/30、attack 125/0、edge 0/24）。
  **复算一律走 `death_report.live_params()`**（meta.params → `dodge_params.json` → 出厂默认）；
  黑匣子落盘必须带 `params=`（`dodge.py` 与 `dodge_gui.py` 已传 cfg）—— 不记下来，事后只能猜。

- **闭环回放不维护 `prev` → 决策序列偏离实机**：`plan()` 的惯性项吃「上一帧**实际执行**的方向」，
  传死 `'none'` 会让自机该停时停不住（实测回放比记录多走几帧、恰好错开真凶，报「未死」）。
  **回放把每帧选中的方向存下来、下一帧传回去**（`replan(..., prev=...)`）。
  另：回放的世界取自记录、不随自机改变（瞄准弹本该改道），结论**偏乐观**，只能当参考。

- **实机复盘的最小余量常在 +0.3px 上下就死了**：判定常数有亚像素误差（自机半径 / grazeSize
  取值、游戏内部判定次序），严格 `<= 0` 会把真凶漏掉、报告只说「没相交」。
  **用 `--tol`（默认 0.5px）判定**，并如实打出「差 0.27px」这种数字。

- **别指望调「安全裕度」(`safe`) 能让自机离弹远一点**：它加在**所有方向**上，排序不变 → 选中的方向一模一样。
  现象：GUI「安全裕度」从 0 调到 5，逐帧选中的方向完全相同。真正决定「贴多远」的是
  `margin`（安全余量权重）——`safe` 只影响「算不算紧张档」与 `risk` 容差。
  **要让它别贴脸就调 `--margin`，不是 `--safe`。**

- **别以为「只躲飞在空中的弹」在密集弹幕里够用**：新弹生成前完全不可见，自机会被逐步压缩到无路可走。
  现象：被击中三次，最优方向间隙都是个位数（1.4 / 8.2 / 4.9px）—— 那一刻已无安全方向；
  而它是被**追上**的（3 秒内从 `dl=21.1` 掉到 `none=1.7`）。
  原因：`plan()` 的间隙只来自对当前活跃子弹的外推（`fx = bx + vx*ts`），
  唯一的未来信息是 `warn` / `warn_dist`，而它只扩大**敌人周围**的半径。
  **密集符卡把 `warn_dist` 调到 100~150、`warn` 调到 30~60** —— 20px 预警圈对覆盖上百像素的弹幕等于没有。
  对照：500 颗弹的道中它能 62 秒 0 次被击中，**问题不在密度本身**。

- **别把「无判定阶段的激光」从安全分里摘掉**：WARN 激光一开火就打人，摘掉等于为躲弹撞进激光。
  现象：48 条激光同时在场时整个场地被算成禁区，所有方向间隙皆负（`none=-12.9 ul=-14.2 down=-25.6`），
  自机选「最不负」的 `none` **站着不动挨打**（16 秒死 14 次）；激光一清零间隙立刻回到 `+56.5`。
  实测 `death_20260927-121323`：那 16 条 WARN 激光**下一帧就全部转成 FIRE**（`ph: 0 → 1`），
  而自机往 `down` 走第 24 帧正好撞上其中一条 —— 「摘掉 WARN」会死得更快。
  **成因不在权重，在排序**：全负时 `min` 只剩「侵入多深」，把「还有几帧不在判定圈里」压掉了。
  **已修**：`plan()` 全负**且走一步就进判定圈**时，改按「窗口内还有几帧不在判定圈里」排
  （`ESCAPE_RANK`，见 DO_NOT_REVERT 同名条）—— 后果兜住，WARN 激光的权重一个字没动。
  仍待用户拍板的候选：预警阶段按剩余帧数**降权**（不与发射阶段等权）——
  它能治成因，但会给安全分引入一个置信度系数，`laser_gap` 的「真实几何」语义要重新定义。

- **别把"激光"当成一种固定几何**：它有三种独立运动，少算一种就漏一种。
  现象：躲过了横扫（轴平移），躲不过旋转 —— 一条 388px 的激光以 2.25°/帧 转，40 帧转过 90°。
  原因：`laser_gap()` 的朝向原本写死成当前 angle；而 `LaserMotion` 一见 angle 变化就把
  该槽速度记 0（当槽复用）→ 旋转激光等于**完全没有运动预测**。
  **三条都要带时间维**：轴平移 `pos + v·t`、朝向旋转 `angle + ω·t`、沿自身伸长
  `end + speed·t`。实测依据与差分做法 → MEMMAP §7.3。

- **别用"几何是否静止"判激光槽复用**：`endOffset` 每帧 `+= speed` 是正常行为，不是异常。
  现象：旧判据要求 `ends` 与 `angles` 都与上一帧一致 —— 于是**所有在生长 / 平移的激光**
  速度都被记 0，只有原地不动的横扫激光拿得到速度。
  **判据换成**：阶段或阶段计时倒退 / 位移超 `MAX_STEP` / 角度跳变超 `MAX_TURN`（三条任一即丢）。

- **别用当前速度给加速弹 / 转向弹做匀速外推**：炸弹幕里这是最大的一类误差。
  现象：算着安全，弹却自己拐过来 / 加速撞上；`0x80` 那类直接朝自机转。
  原因：子弹每帧**先按 exFlags 更新 velocity，再 `pos += velocity`**（MEMMAP §2.1）：
  `0x10` 每帧 `velocity += accel`；`0x40/0x80/0x100` 在 `timer >= interval×(num+1)` 那一帧
  把速度矢量整体改向，间隔内速度还线性衰减到 0。
  **走 `bullet_paths(bf, …)`**（输入 `read_bullet_frame()` 的 exFlags 与运动参数），
  别再自己写 `bx + vx*t`。

- **别把软项的前瞻一刀切**：用统一的 `ATTACK_STEP`（4 帧 = 18px）评「这一带弹多不多」，软项几乎不起作用。
  现象：空旷区吸引开 / 关的**决策差异率只有 1.2%**、空旷度 0.205 vs 0.205（等于没生效）。
  原因：9 个候选方向的落点彼此只差几十像素，而评价半径 110px → 各方向的空旷度高度相关。
  实测（真实密集快照 120 帧）前瞻 vs 同帧极差 vs「最空旷方向贴着边界」的比例：
  4 帧 0.20/2%、8 帧 0.51/2%、**12 帧 0.85/2%**、16 帧 0.98/12%、20 帧 0.99/38%、25 帧 0.99/78%。
  **评「区域」的项要给它自己的前瞻**（`CLEAR_STEP = 12`），别跟着评「这一步落在哪」的项走；
  但**别超过 16 帧** —— 20 帧起近四成的帧会把自机往边界赶。
  落地效果（前瞻 12 帧）：差异率 10%、空旷度 0.199→0.161、平均安全分 12.91→**14.37**、
  最差单帧 **0.00px**（旧 4 帧前瞻是 −11.03px）。复现：`_tmp/sweep_clear.py`（读 `_tmp/dense_frames.pkl`）。

- **别把空旷度的评价半径拉满**：空旷区吸引「调了没反应」。
  现象：`clear_r = 999`（手输超滑条上限 200）时九向空旷度**全部饱和到 1.0** ——
  120 帧真实快照实测「九向完全同值」占 **100%**、开/关决策差异率 **0.0%**；
  权重再大也无效（25 与 100 同为 0.0%），因为软项对每个方向减的是同一个常数。
  原因：软化计数除以 `CLEAR_REF = 32` 后 clamp 到 [0,1]，而 999px 半径覆盖整个场地 ——
  任何落点都「看得到」全部弹（密集符卡弹数 82~163 > 32）→ 计数恒 ≥ 参考值 → 恒为 1.0。
  实测区分度随半径：60px 极差 0.133、**110px 0.846（默认，有效）**、
  200px 0.309（**10% 的帧九向同值，且安全分 10.49→7.70、最差单帧 −26.55px**）、
  999px **0.000（100% 同值，完全失效）**。
  **半径留在 110 附近、别超 ~150；要更强的空旷吸引就加权重（0~60），不是加半径。**
  判据是**软化计数 vs `CLEAR_REF`**：计数 ≥ 32 即饱和（密集符卡必饱和）；
  稀疏场面（如 16 颗弹散开）下 999px 仍能算出极小差异（极差 ~0.025），
  而 110px 下 `cost` 会**合法地为 0**（落点周围根本没弹）—— 那不是失效，是没弹可躲。
  看 `explain_plan.py` 的「空旷项」列全 0 时先查弹数：< 30 颗属正常，别误判。
  同类退化不限本项：**任何「半径 / 窗口」类参数拉到覆盖全场都会饱和成常数**。
  复现：`_tmp/diag_clear_r.py`（读 `_tmp/dense_frames.pkl`，不依赖游戏）。
  入口侧防护：GUI 的 Spinbox 只挡箭头、**不挡键入**，现在超范围会打印告警（`dodge_gui.warn_range`）。

- **别把空旷度当成「弹少 = 好」**：开了空旷区吸引，自机爱往角落钻。
  现象：用户报「开了空旷区就躲角落」。120 帧真实密集快照 + 90 帧影子推演实测
  「终点落在角落（离边界 < 80px）」的比例：**关掉 8% → 权重 25 时 31% → 权重 60 时 42%**。
  原因：空旷度只问「这一带弹多不多」，而弹幕从上往下生成、**边角天然弹少**；
  权重 60 时「空旷项收益压过边界惩罚」的帧占 **98%**（收益中位 12.15 分 vs 惩罚 3.10 分）。
  **加大回中与贴边都压不住**：回中 25→40 角落率纹丝不动（42%），贴边 42→120 只从 30% 到 29% ——
  贴边惩罚只在落点离边界 < 60px 内生效，而角落方向的落点大多落在 60~110px 之间。
  **改法：密度按「圆落在场地内的可用面积」归一**（`clear_area_frac`）——
  边角那个圆有一小半在场地外（实测左下角 40px 处只有 0.54），那里弹少本来就是假象。
  落地后角落率 42%→30%（权重 60）、31%→26%（权重 25），
  **安全分与最差单帧完全不变**（23.43 vs 23.51；同为 −16.75px），
  `plan()` 单次 0.83ms（帧预算 5%）。
  **反例（别这么做）**：把贴边方向的空旷度直接「顶到最挤」能把角落率压到 4%，
  但安全分从 24.30 掉到 **17.17**、最差单帧 **−40.52px** —— 那等于用边界偏好
  覆盖了真实弹密度信息，空旷项就不再是「往弹少处退」了。
  复现：`_tmp/diag_clear_corner.py`（单帧倾向）、`_tmp/shadow_corner.py`（推演）、
  `_tmp/exp_area_clear.py` / `_tmp/exp_area_effect.py`（改法与反例对照）。

- **别以为「预警阶段不动」就等于「它不会扫过来」**：这是 Laevatein 躲不开的真正原因。
  现象：自机盯着一条静止在屏幕最左的预警线（离自己 140px）继续输出，等它开火，
  18 帧内被追上打死 —— 用户原话「激光要出了还在打敌人，而不是立即远离」。
  原因：实测预警期 `pos` 静止、`speed = 0`，**开火后才 +6px/帧横扫**，
  「它会不会扫、往哪扫」在预警期**完全没有信号**；而横扫 6px/帧 > 自机 4.39px/帧，
  横向怎么跑都被追（它会扫过整个屏幕宽度），只有沿轴线跑出 368px 长的区间（30+ 帧）才安全。
  **改法：预警激光做矩形避让（`dodge.WARN_RECT_W` 软项）—— 请自机沿轴线走出它的区间，
  别把「横向余量」当安全。必须走软项：它的量纲是「逃出区间还需多少」，
  混进安全分会把「撞敌人 −10」盖掉（实测：自机为了躲激光径直撞进 BOSS）。**
  → CONTEXT §3.23

- **别用一步的前瞻去评「该不该离开某片区域」**：矩形避让第一版跟着 `ATTACK_STEP`（4 帧），
  开 / 关的决策差异只有「right → ur」这么一点，**等于没生效**。
  原因：4 帧的落点彼此只差十几像素，而激光区间长 368px，各方向的「深浅」几乎一样。
  **给它自己的前瞻**（`WARN_RECT_STEP = 24` 帧 ≈ 105px）后，方向差异才分得开。
  同款坑见 `CLEAR_STEP`（空旷项）；判据是「同帧极差」与「开/关决策差异率」。

- **别把激光的 `pos` 当固定值**：激光会**整体横扫**，而槽里的 `speed` 字段测不到它。
  现象：Laevatein 里自机贴着激光右边缘跑（余量只剩 0~3px），被从后面追上打死。
  原因：`speed`（`+0x26C`）只描述 `endOffset` 前进（实测横扫激光恒为 0）；
  移动发生在 **`pos`** 上（实测 **+6px/帧** > 自机 4.39px/帧），
  槽里没有这个量，只能逐帧差分（`dodge.LaserMotion`）。
  同源的第二处错误：线段起点要加 `startOffset`（`pos` 是**轴原点**，不是起点），
  旧实现按 `[pos, pos + startLength]` 算。
  **改法：`laser_gap()` 必须带 `ts` 并同时吃 `lspeed`（offset 前进）与 `lvx/lvy`（轴原点平移）
  —— 单帧读值算不出横扫。** → MEMMAP §7.1、CONTEXT §3.23

- **别指望「自动回中」在有弹幕时把它拉回中心**：它是软项，安全分永远优先。
  现象：符卡中自机照样贴到底边（y=432）与左边界（x=36.6）；回中项只在**同等安全**的方向间起作用。
  这符合设计（先活下来，再谈站位）—— 它真正明显的效果在**空档期**：无威胁源时自机被锁在中轴线上
  （实测 x 恒为 193.8，场地中心是 192）。
  **要更主动回中就把 `--center` 调大、`--center-r` 调小**，别把它当「强制回中」用。
  副作用：空档期在自由半径内没有梯度、又没有阻尼，自机会在带内来回游走（无危险，仅观感）。

- **别用 sleep 计时刻量自机速度**：0.5s 估出「右 +92 / 上 −88 / 左 −36」三个互相矛盾的值。
  原因：sleep 精度与按键送达延迟让实际按住帧数少于 30；左移 36px 是撞到左边界，不是速度。
  **改用帧计数 `0xC21C00` 计帧、每方向先归中、起点离边界不足就作废**（`tools/calib_speed.py`）。

- **速度标定的出发点不能用场地正中心**：8 个方向全部报「距边界不足 212px」直接跳过。
  原因：中心到上下边界只有 208px，而 `need = frames×5+12 = 212px` —— 归中点与余量校验互相矛盾。
  **每方向归到该方向的「反侧」出发点**（`start_spot()`），正向余量 328~376px。

- **从非前台进程抢游戏前台会被 Windows 拒绝**：`✗ 游戏未取得前台焦点`，一个键都不发。
  原因：系统只允许「前台进程 / 由前台进程启动 / 刚收到输入」的进程抢前台。
  现象：从 agent 的 shell 跑必定失败；用户自己从终端或 GUI 按钮跑则成功。
  **标定与实跑要么由用户触发，要么先手动把游戏切到前台**；别把它当脚本 bug 去改 `set_foreground`。

- **别把中心吸引 / 惯性直接加在安全分上**：软项会盖过真实间隙，选中必死方向。
  现象：贴脸弹 + 贴边权重 30 时，旧公式选中「时间窗最小间隙 = −0.25px」的方向。
  **分两层：有方向间隙 ≥ `comfort` 才让软项决胜负，否则只比安全分。**

- **别把贴边项写成全局中心吸引**：它与进攻吸引在全场持续对抗，把自机钉在原地。
  现象：自机要右移 30px 对齐目标，却被「离中心远」劝回，水平偏差 53px 打不到敌人。
  **用 `edge_cost()`：只在离边界 `EDGE_MARGIN`(60px) 内扣分，场地中部为 0。**

- **软项的前瞻尺度必须短**：用 `horizon`(30 帧=120px) 外推评估软项，会把「朝边界走一步」
  当成「一路撞到边界」。现象：自机要右移 30px 对齐目标，被外推撞边界的预测劝退，精度差 27px。
  **软项统一用 `ATTACK_STEP`(4 帧) 前瞻位置；安全分仍用完整 horizon 轨迹。**

- **进攻项不惩罚「冲过目标头顶」就永远打不到敌人**：旧式 `max(0, (y-ty)-standoff)`
  在自机跑到目标上方后恒为 0，与理想位置同分，冲上去就不回来；子弹朝上飞，头顶打不到。
  **`attack_cost()` 垂直项分段：带内 0、带外驱动靠近、头顶按 `OVERSHOOT_W` 受罚。**

- **切换门槛别超过 0.5**：会把「贴着边界该往右脱出」也粘住，还让自机停在半路不对齐目标。
  实测：门槛 0.3 → 对齐 0.8px；1.5 → 停在中途偏差 139px。
  **保持默认 0.3；去抖靠安全余量与进攻项死区，别靠加大门槛。**

- **进攻吸引（`--attack`）把自机往敌人方向拉**：`pick_target()` 只认上方敌人，
  停在哪由进攻项死区 `standoff..standoff+ATTACK_REACH` 决定。
  **`--standoff` 是输出带下沿：调 0 会让它一路贴到敌人脚下；保持默认 48px，想更凶每次降 8px。**

- **道具吸引的前瞻加长会「追不动」**：把道具项从前瞻 4 帧换成 15 帧后，自机停在距道具
  **19px** 处不动，看着像吸引力太小，其实是终点距离模型把「再走一步就够到」
  （拾取半宽 14px）误判成「冲过头」。
  **道具项沿用 `ATTACK_STEP`(4 帧)**：方向间吸引差 1.42 已远大于切换门槛 0.3，够用
  （`check_plan.py` 用例 13 钉住）。

- **没有威胁源时不能照旧拦截软项**：无弹 / 无敌人 / 无激光时安全分恒为 0 < `comfort`，
  软项被整体跳过 → 自机全程 `none`，清完杂兵的空档期掉落物在眼前也不捡。
  **此时所有方向都绝对安全，直接让软项决胜负**（`dodge.plan()` 的 `has_threat`）。

- **道具的「可接性」判据别写成 `FIELD_Y1 - y`**（自机当前位置）：那样「自机越高、预算越大」，
  道具项会自己驱动自机往上跑。现象：自机要往右对齐道具，却选了 `ur`（右上）。
  **剩余时间只由道具决定**（`FIELD_Y1 - iy`）；越靠上越安全的项一律不许进软项。

- **「干等」要按「到位后还要空等的帧数」算，不能按总时长算**：按总时长会把
  「边横移边等它落下来」也判成干等，把本来接得到的道具一起劝退（收集率掉一截）。
  **`idle = max(t_arr − t_go, 0)`**：自机到位时道具正好到 → 不罚。

- **道具项对垂直位置的牵引必须受限**（`ITEM_DOWN_REACH`，默认 20px）：不设它时自机会为了
  追已经落过自己的道具上下游走、离开输出带（仿真：输出带内帧 1618 → 700）；设太大（≥30px）
  收集率反而下降（55% → 48%）—— 追下方道具要离开输出位，收益还不如等下一颗。
  **别把它当无用参数删掉，也别为了「多捡点」调大。**

- **state-2 散射物的 vy 字段是垃圾值**：散射 60 帧插值期间，`+0x20` 被 `SpawnItem` 用
  出生点 y 覆写（实测值像 −123 这种坐标，不是速度）。拿它外推会把散射物判成「早就该到」
  或「永远到不了」。而且散射结束后 vy 清零、从静止重新 +0.03 加速，state 永不转 0，
  **也永远不被收集线转化**（原版转化判据在 `state != 2` 分支里）—— 把它算进冲线的
  可转化价值，会让触发阈值虚高，冲上去什么也没吸到。
  **近似法（`read_frame()` 已落盘）**：位置用 targetPosition、vy=0、`delays` 平移到达/出局
  时刻（模型本身不动）；`poc_val` 只合计 state-0；state-1 追踪中的自投罗网，剔除出吸引集。
  依据 → MEMMAP §9 末段；护栏 `check_plan.py` 用例 34–35。

- **集群加成只改价值（vals），不碰 item_cost 的几何**：曾考虑「朝道具密集处直接加一项
  位置吸引」—— 那等于开了第二个吸引模型，干等/白跑/错过三件过滤全要重写一遍。
  现在的做法是让一片道具互相抬价（`item_cluster_vals`），等效距离的分母变大，
  「往哪走」自然变成「一趟能捡最多」；过滤仍由 `item_cost` 单点把守。

- **反应延迟调太大反而更抖**：`react` 从 4 调到 8 后，对齐场景的方向切换 4 → 16 次，
  密集弹幕的全程最小间隙 21.1 → 18.6px —— 本想"更像人"，结果既更机械又更危险。
  原因：延迟与切换门槛叠加 —— 迟几帧才动，动完已经过冲，下一帧又要回摆。
  **默认 4 帧（≈67ms）是实测拐点；要调大先跑 `py tools\humanize_sweep.py` 看三个判据。**

- **延迟的判据写"最优方向安全"是不够的**：延迟期间自机走的是**当前方向**，不是最优方向。
  判据必须同时要求 `scores[cur] ≥ comfort`，否则会出现「最优方向很安全、但脚下这条路已经在死路上」
  却还在等的局面。
  **两条一起判**（`ReactionGate.update()`），护栏 `check_plan.py` 用例 21 钉住 9 种违反组合。

- **`screen_of()` 见到自机死亡就退出主循环，把抢救机会吃掉了**：`dying` 标志一置位，
  它返回 `DYING` + `ok=False`，`run_session` 当场松键退出 —— 而此时死亡窗口还剩 7 帧。
  原因：画面判据是「发键前的安全闸」，写在主循环最前面；灵击决策排在它后面就永远轮不到。
  **灵击必须在画面判据之前跑**，窗口内（`state == DEAD 且 respawn > 0`）不退出；
  被救回后 `dying` 标志可能还滞后着，但 state 已不是 DEAD，也要继续跑（`salvaged` 判据）。

- **别用 `respawn < 8` 当「死亡窗口」判据**：存活时它实测恒为 8，但原版复活后会赋成 6
  （`Player.cpp:287`）—— 拿 8 当基线会把刚复活的自机误判成"正在死亡"，白扔炸弹。
  **判据用 `state == DEAD 且 respawn > 0`**（`state` 在 `Player+0x7898`），
  `respawn` 只当"还剩几帧"的参考读数。护栏 `check_autofire.py` 的灵击用例钉住。

- **无敌 / 复活中做必死预判 = 白扔炸弹**：`state` 是 INVULNERABLE(3) 或 SPAWNING(1) 时
  自机本来就死不了，可九向必死判据照样会成立。
  **预判那条路只在 `state == ALIVE` 时走**；死亡炸弹那条不受影响（DEAD 才触发）。

- **同帧 `key_down` + `key_up` 等于没按**：bomb 是**按下沿**触发（`0x68A09` 要跟上一帧的
  输入位图比）。游戏每帧只轮询一次键盘状态，同帧完成的 down+up 可能整个落在两次轮询之间，
  游戏看到的是"两帧都没按"。
  **按住 `BOMB_HOLD`(3) 帧再松开**；也别一直按着 —— 那样只有第一帧算。

- **敌人也会动，而且池里读不到速度**：前瞻把敌人当静止的 → 自机算「这一格安全」，
  走过去时 BOSS 已经挪到路上。现象就是用户报的「撞到敌人身上死亡」。
  原因：子弹有 `vx`/`vy`、激光有 `LaserMotion`，**只有敌人没有运动预测**。
  **用 `EnemyMotion` 逐帧差分**（判据同 LaserMotion：`life` 只减不增 + 位移 ≤ `MAX_STEP`），
  再由 `enemy_gap(..., evx, evy, ts=ts)` 按帧外推；另加 `ENEMY_MARGIN` 余量。

- **Laevatein 的激光是竖线，而唯一的出口正是 BOSS**：CSV 实测 `angle = 90°`，
  线段沿 y 铺满整个场地（y ∈ [80,448]），所谓「从左到右扫」= 这条竖线每帧 +6px
  水平平移。水平跑不掉（6 > 自机 4.39），只能上下走出端点 —— **上方端点就是蕾米莉亚**
  （AABB 56×56、y ∈ [52,108]）。
  **所以「沿轴往外走」这条偏好永远不能进安全分**：它等于把自机直接送进 BOSS。

- **别再拿菜单/死亡画面的采样去验证战斗逻辑**：`screen` 字段是 `MENU` / `CONTINUE` /
  `NO_LIVES` 时，激光池里只有**残留数据**，拿它跑 replay 得到的「安全分没变」毫无意义。
  **先查采样期的 `screen` 分布**，确认有战斗帧再用。

- **别假设从配置来的 `horizon` 是 int**：控制台存盘是 JSON，数值一律浮点（实测 `"horizon": 20.0`）。
  现象：实机一跑就 `TypeError: expected a sequence of integers or a single integer, got '20.0'`。
  原因：`np.arange(1, horizon + 1)` **容忍**浮点（老代码因此一直没暴露），
  但 `np.full(horizon, ...)` 与 `g[:horizon]` 都要求 int —— 新加的代码撞上了前者。
  **改法：`plan()` 入口处 `horizon = int(horizon)`（一处治愈）；
  护栏必须喂存盘格式（`20.0`）而不是字面量 `30`，否则抓不到这类崩。**
  护栏：`check_plan.py` 用例 49（浮点不崩 + 与整数结果逐字一致）。

- **别用 `iconbitmap()` 的返回值验图标，也别用 `windows`/`shotwin` 量 Tk 子窗口**：
  `iconbitmap()` 查询恒返回空串（不代表失败）；日志窗口实际 640×400 而 `windows` 报 608×134；

- **启动游戏必须走 Steam**：直接运行 `th06nc.exe` 会因 `SteamAPI_RestartIfNecessary` 立即退出。

  **用 `steam.exe -applaunch 4659620` 启动。**

- **改了 `tools/` 下的代码，控制台行为却一点没变**：日志里的报错跟修改前一模一样。
  原因：Python 在 import 时读模块，之后**不会重载** —— 控制台进程仍在跑启动那一刻的代码。
  曾因此把"已修好的 bug"误判成"没修好"，白追一轮。
  判据：`Get-Process pythonw | Select StartTime` 与文件 `LastWriteTime` 比对。
  **改完 `tools/` 里任何文件都要关掉控制台重开**（桌面快捷方式重开即可）。

- **GUI 跑几秒就 `SCENE_None` / 「读取失败」**：CLI 版能连跑 1500 帧，GUI 版第一次实战就崩。
  原因：`Process.read` 复用一块 1MB 缓冲**和返回长度**，而 GUI 主线程（状态刷新）与躲避线程
  共用同一个 `Process` —— 只读实验实测并发读取 **33% 长度错位**（小读拿到大读的长度）。
  **`read()` 已加锁**；别在别处绕过它直接调 `ReadProcessMemory`。同理，躲避运行中重连会
  close 掉正在用的句柄，GUI 已拦截。

- **给 `run_session` 加了新的读取依赖，只跑了它自己的用例**：`check_autofire.py` 立刻
  `AttributeError: 'NoneType' object has no attribute 'read'` —— 它是桩化跑的（`p=None`），
  而新读的那一项没桩。
  原因：`run_session` 每帧调用的每个读取函数都是它的**隐式依赖**，桩化测试必须逐个覆盖。
  **在 `run_session` 里新增 `read_xxx(...)` 时，同步给 `check_autofire.py` 的桩补上同名 lambda**；
  跑一遍 `check_autofire.py` 就是判据。

- **`SendInput` 的键在系统看来也是「按键」**：低级键盘钩子收得到，`GetAsyncKeyState` 更分不出人机。
  想让「人在操作」这件事可判，只有两条判据合用：`KBDLLHOOKSTRUCT.flags & LLKHF_INJECTED`
  与自写的 `dwExtraInfo` 标记（`th06.INJECT_TAG`）。
  **别用 `GetAsyncKeyState` 或「键状态变化」做让位判据** —— 脚本会被自己发的键触发。

- **`SetWindowsHookEx` 收到被截断的 hMod 会直接失败**：`GetModuleHandleW(None)` 不设 `restype`
  时按 c_int 返回，64 位下句柄被截成 32 位，钩子装不上（`start()` 只返回 False，看不出原因）。
  **给 `GetModuleHandleW` 设 `restype = wintypes.HMODULE`**，并让钩子线程跑 `GetMessageW` 消息循环
  （低级钩子的回调是在装钩子的那个线程里被调用的，没消息循环就收不到）。
  判据：`py tools\human_watch.py --seconds 5` 里「注入事件」计数必须 > 0 —— 否则钩子压根没工作，
  「注入键没被算成真人按键」只是假通过。

- **`SendInput` 的抬键会改系统键状态表**：让位时无脑 `release_all()` 会把玩家正按着的方向顶掉 ——
  人家按住右键，脚本发一次 `key_up(right)`，游戏读到的就是「松开了」（键盘自动重复要几百毫秒才补回来）。
  **抬起前跳过玩家物理按住的键**：`release_all(held, skip=watch.physical())`。

## 打包发布

- **打包后所有由 `__file__` 推导的路径都指向只读解包目录**：源码版正常的「保存参数 / 写地址缓存」
  在打包版静默失败（异常被 `try` 吞掉，用户只看到"没生效"）。原因：PyInstaller 把 `__file__`
  指到 `_internal/`。
  **凡是要写文件的路径一律走 `tools/paths.py`**：可写用 `paths.app_dir()` / `paths.outside()`，
  只读资源用 `paths.res()`。新增写盘代码前先想一遍"打包版写到哪"。

- **`sys.executable` 在打包版就是 exe 自己**：`subprocess.call([sys.executable, 'autofix.py'])`
  会再启动一个控制台（或静默失败）。原因：frozen 后没有 `.py` 可解释。
  **改走内部子命令 `exe --run autofix`**（`app_main.run_subcommand`）。子命令分支必须放在
  `_fix_streams()` **之后** —— windowed 版 `sys.stdout is None`，子命令里第一句 `print` 就崩。

- **`.pyw` 既 import 不进来，也进不了打包依赖树**：Python 的源码后缀只有 `.py`。
  **实现放 `.py`、`.pyw` 只留壳**（`launcher.pyw` → `app_main.run()`）；桌面快捷方式指向壳，不受影响。

- **构建脚本的冒烟测试会把构建卡死**：exe `--check` 在 windowed 模式下弹模态窗等人点确定。
  **冒烟时设 `TH06NC_NO_ALERT=1`**（`app_main.alert` 只在该变量缺失时弹窗）。

- **PowerShell 5.1 按 ANSI 读无 BOM 的 `.ps1`**：脚本里的中文变乱码，甚至引号解析出错。
  本机没有 pwsh 7（`powershell` 就是 5.1），CI 与用户机器都可能中招。
  **`tools/*.ps1` 存成 UTF-8 带 BOM**；改完用 `[IO.File]::ReadAllBytes()[0..2]` 核对。

- **`2>&1 | Select-String` 会让成功的构建报 `exit code 1`**：PyInstaller 把 INFO 日志写 stderr，
  PowerShell 视作错误记录，现象与真的构建失败无法区分。
  **判据看产物**（zip 与 `SHA256SUMS.txt` 是否生成、时间戳是否新）；脚本末尾显式 `exit 0`。
