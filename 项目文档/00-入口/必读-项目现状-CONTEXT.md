### 3.7 决策分层：软项不覆盖安全

`plan()` 先比安全分（时间窗最小间隙），再分两档：

- **宽裕档**（存在方向间隙 ≥ `comfort`，默认 1px）：贴边 / 惯性 / 进攻 / 道具在够安全的方向间决胜负。
- **紧张档**（最优方向间隙 < `comfort`，boss 战弹幕密时是常态）：只允许**间隙 ≥ 0 且与最优方向
  相差 ≤ `risk`**（默认 1px，本就落在外推误差量级）的方向参与软项排序；`risk = 0` 退回纯躲。
  此前紧张档一律只比安全分 → boss 战全程只躲不打。

两档的池内排序 = 软项 + 安全余量（间隙越大越优先，上限 24px；基准分别是 `comfort` / 最优间隙），
再过切换门槛（默认 0.4）迟滞。软项与安全分同量纲相加曾是主缺陷（会选中必死方向）。

**激光另留一截余量**（`LASER_MARGIN`，默认 16px）：激光不动、一道能挂几十帧，只按「别撞上」
算的话间隙刚过 `comfort` 就算安全，软项立刻把自机拉回激光边上输出 —— 惯性 / 反应延迟一推
就滑进去（实测报的「撞激光上」）。它**只加在躲避的安全分上**，必死预判仍用真实几何。
护栏 `check_plan.py` 用例 36。

### 3.9 自动攻击 + 进攻跟随

- **射击**：进关卡后一直按住 `Z`（按住才连射；`tap` 只出零星几发）。
  退出 / 前台切走一律先松开 —— 发键只有一个出口 `apply_fire()`。
- **走位**：`pick_target()` 选目标（BOSS 优先，只认自机上方的敌人 —— 子弹朝上飞）；
  `plan()` 的软项多一项**进攻吸引**，与贴边/惯性同层：宽裕档全权重参与，
  紧张档只在「与最优同样安全」（相差 ≤ `risk`）的方向间参与。
  进攻项按 `ATTACK_STEP`(4 帧) 前瞻评估，垂直方向是死区：停在目标下方

  头顶子弹朝上飞，永远打不到。
- **参数**：`attack`（默认 30，0 = 不追）、`standoff`（默认 99px）、`risk`（同等安全容差 1px）、

### 3.11 自动捡掉落物（时间模型 + 顺路）

- **读取**：`tools/read_items.py` —— 整块读 1024 槽道具（352 KB，约 0.3 ms）→ 位置 / 类型 / 下落速度 `vys`。
  下落规律（原版反编译确证）：vy 从 −2.2 起每帧 +0.03 到 3.0；**y ≥ 432 消失且倒扣 rank**（漏捡有代价）。
- **决策**（`item_cost()`）：等效距离 = 需要移动的距离 ÷ (时效 × 价值 × 错过程度)。三项时间判据：
  - **不干等**：自机到位后还要空等的帧数 > `item_wait`（默认 60 帧）→ 现在不追，等它降下来再对齐；
  - **不白跑**：到位所需帧数 > 道具落出场地前剩余帧数 → 出局；
  - **不上追**：垂直只在道具位于自机下方时计入，且不超过 `ITEM_DOWN_REACH`(20px) ——
    自机只做水平对齐，等道具落到身上。
- **顺路**（`item_aim_vals()`）：有可打目标时，道具水平位置离目标对齐线越远价值越低
  （±40px 内满值，±136px 外归零）。打得到 → 敌人才会死 → 才继续掉道具。
- **空档期不呆立**：场上无威胁源时安全分恒为 0、低于 `comfort`，旧逻辑会把软项整体拦截 →
  自机全程 `none`。现在此时所有方向都绝对安全，直接让软项决胜负。
  火力未满时 Power 类价值 ×1.8；满火力后蓝点更值钱。
- **空档期主动等落点**：没有中弹风险时把 `item_wait` 放宽到 `ITEM_WAIT_IDLE`(600 帧) ——
  「先走到落点下方等它掉下来」不是干等而是主动捡；有威胁源时仍按 `item_wait` 拦（不为道具站桩）。
  护栏 `check_plan.py` 用例 16b–16d。
- **参数**：`item`（默认 50，0 = 不捡）、`item_wait`（60 帧）；GUI 有滑条，`--no-item` / `--item-wait`。
- **实证**：护栏 `check_plan.py` 用例 12–16 / 13b–13e / 27–28（含旧「瞬时距离」模型对照）；
  取舍数字 → `py tools\item_sweep.py`（新模型：收集率 47%→55%、对准 boss 帧数 352→315，5 种子平均）。

### 3.12 弹幕预警（预测「下一波还有几帧来」）

- **依据**：敌人结构里的 `shootInterval`(`+0xF68`) / `shootIntervalTimer`(`+0x10A4`) ——
  反汇编 `0x28A8A` 段完整确证：`inc timer` → `cmp timer, interval` → `SpawnBulletPattern` → `timer = 0`。
- **做法**：倒计时 = `interval - timer`；倒计时越小，该敌人的**危险半径**越大（`warn_radius()`），
  把自机提前挤出弹幕覆盖区。**改的是安全分本身，不是软项。**
- **只预测时机，不预测形状**：形状要解析 `bulletProps`，而新典该结构布局与原版不同（未反推完）。
- **参数**：`warn`（窗口帧数，默认 10，0 = 关闭）、`warn_dist`（最大额外半径，默认 10px）。
- **验证**：`read_enemies.py` 会打 `★N帧后发弹`；护栏 `check_plan.py` 用例 17–18
  （该方向危险分 104.8 → 53.8px）。**倒计时逐帧递减待实机复核**（采样时游戏停在 Continue，`interval = 0`）。

### 3.13 人类化反应延迟（安全时慢半拍，危险时零延迟）

- **为什么**：原来每帧（60 Hz）重决策并立即发键 —— 零反应延迟本身就是机械特征。
  真人高手的反应时间**随紧张程度变化**：危险时即时反应，安全时从容。
- **做法**：`plan()` 与按键之间加一层 `ReactionGate`（`tools/dodge.py`）：局面宽裕时把新方向
  先挂起几帧再执行；延迟长度逐次随机抖动（`REACT_JITTER`）—— 固定帧数节奏本身就是机械特征。
- **只在安全侧**：延迟期间走的是「当前方向间隙 ≥ 底线」这条路，且最优方向要多留
  `REACT_SLACK`(8px) 才敢等；无威胁源（空档期）直接视为绝对安全。任一不满足 → 当帧执行。
  `plan()` 的间隙已覆盖 horizon 帧外推，远长于几帧延迟，所以慢半拍仍在已确认安全的轨迹上。
- **底线与「安全分数线」解耦**：判据用 `max(comfort, REACT_MIN_COMFORT(6px))`。分数线同时是
  软项的闸门，为「让更多软项参与」把它调到 1px 是合法调参 —— 但延迟不该跟着放松（实测有人
  这么调过，等于把延迟闸门从 6px 拉到 1px）。调高分数线时从严，调低时不放松。
- **`prev` 语义变了**：传给 `plan()` 的是**实际执行**方向（延迟后），不是 plan 的原始输出 ——
  否则延迟期间 inertia / 切换门槛会以为自己已经在走新方向。
- **参数**：`react` 默认 7 帧（`REACT_FRAMES`；仿真拐点是 4 帧，7 为用户实机沿用值），
  0 = 关闭；GUI 有滑条，`--react` 可覆盖。
- **实证**（`tools/humanize_sweep.py`，240 帧闭环）：密集弹幕方向切换 38 → 13 次（−66%），
  最小间隙不变（21.1px），对齐 1.3 → 4.9px（敌人半宽 14px，仍打得中），道具拾取不受影响；
  调到 8 帧则对齐场景切换升到 16 次、最小间隙降到 18.6px → **4 帧是拐点**。
- **护栏**：`check_plan.py` 用例 19–24（0 = 关闭 / 安全时确实等且有界 / 危险侧 9 种组合零延迟 /
  目标反复变不卡死 / 空档期允许从容 / 分数线调低不放宽延迟）。

### 3.15 自动灵击（被打中时放技能）

- **依据**（反汇编 `Player__OnUpdate` + 原版 `BombData.cpp` → MEMMAP §11）：
  bomb 是**按下沿**触发（输入位图 bit1），且要求 `respawnTimer != 0`。它存活时恒为 8，
  被击中进 DEAD 后逐帧递减、**到 0 才结算掉命** —— 这 8 帧里按 X，角色 bomb 的 calc 会把
  `playerState` 改成 INVULNERABLE，**死亡就此取消**。这就是死亡炸弹，真人高手的标志操作。
- **两条触发路径**（`BombGuard`）：
  - **死亡炸弹**：`state == DEAD 且 respawn > 0` —— 被击中后立刻按 X 抢救；
  - **必死预判**：九向外推 `bomb_pre` 帧全部与威胁重叠（`doomed_gap() < 0`）—— 判据为负
    意味着不炸必死，所以这一炸不会浪费，且抢在碰撞判定之前生效，比死亡炸弹更稳。
    **激光只喂「发射中」那一组**（`laser_armed`）：预警 / 消散阶段打不到人（阶段语义 → MEMMAP §7.2），
    混进来就会在激光还没释放时白扔炸弹。躲避仍看全部阶段 —— 预警线就是马上要开火的位置。
- **不浪费的三道闸**：`bombs > 0`、当前没有灵击在生效（`bombInUse`）、必死预判只在
  `state == ALIVE` 时做（无敌 / 复活中本来就死不了）。
- **发键**：按住 `BOMB_HOLD`(3) 帧再松开，之后静默 `BOMB_COOLDOWN`(10) 帧 ——
  按下沿必须跨帧存在，同帧 down+up 会被游戏轮询漏掉。`X` 与方向键同走 `apply_keys`，
  退出时由 `release_all` 统一松开（发键仍只有一个出口）。
- **必须在画面判据之前**：`screen_of()` 见到自机死亡会返回 `DYING` 让主循环退出 ——
  抢救接在它之前，窗口内不退出；被救回后（state 不再是 DEAD）即使 `dying` 标志滞后也继续跑。
- **参数**：勾选「自动灵击」（默认开）、滑条「必死预判提前」（`bomb_pre`，默认 1 帧，
  0 = 只做死亡炸弹）；CLI `--no-bomb` / `--bomb-pre`。
- **护栏**：`check_autofire.py` 灵击用例 12 项（窗口内按 X / 没炸弹不按 / 窗口过了不按 /
  九向必死才预判 / 无敌中不预判 / 关掉后不发 / 安全时不乱炸 / 激光预警不预判 / 激光发射才预判 /
  激光阶段过滤 3 项）。

### 3.16 道具集群 + 智能道具线（PoC 全屏吸）

- **集群价值**（`item_cluster_vals()`）：每块道具的有效价值 += 邻居价值 —— 一片道具挤在
  同一落点附近时「朝那里走一趟能全收」，等效于单块价值翻倍。方向选择从「最近/最值钱的一块」
  变成「一趟能捡最多的一片」。邻居判据：水平窗 `ITEM_CLUSTER_WIN`(56px) + 到达自机高度的
  时间差窗 `ITEM_CLUSTER_T`(60 帧) + 邻居可捡（快掉出场的按 `ITEM_SURV_REF`(60 帧) 缩水）。
  只改 vals 不动 `item_cost` 几何（等效距离的分母变大，过滤仍由它单点把守）。
- **道具三态分拣**（`read_frame()`，依据 MEMMAP §9 + 原版 `ItemManager::OnUpdate`）：
  state 0=普通下落（正常吸引）；1=已被吸引（8px/帧追自机，自投罗网 → 剔除出吸引集）；
  2=散射（60 帧插值到 targetPosition，期间 vy 字段是出生点 y = 垃圾值；散射结束 vy 清零、
  state 永不转 0、永不参与转化）→ 位置用终点近似、vy=0、`delays`=平均剩余 30 帧
  平移到达/出局时刻（`item_cost` 模型不动）。
- **智能道具线**（`ItemLineTrip`，机制依据 → MEMMAP §9 反汇编 0x42980）：满火力(128) 且
  自机 y<128 时游戏把全屏 state-0 道具强制转追踪（8px/帧飞向自机，不可能漏捡）。状态机：
  满火力 + 可转化价值（state-0 合计）≥ `poc_min`(默认 0.0) + 自机在线下 → charging
  （冲线目标 = 非追踪道具价值加权质心 x + `POC_TARGET_Y`=120）；越线即成功回 idle；
  限时 `POC_TIMEOUT`(300 帧) / 价值见底 / 火力掉了 / 被关掉 → 放弃进冷却 `POC_COOLDOWN`(240 帧)。
- **冲线吸引走软项通道并替代进攻/道具吸引**（不是叠加）：`poc_w = attack + item + POC_W_EXTRA(8)`。
  attack_cost 的「冲过头顶」惩罚专治输出位，冲线时往上冲正是目的，留着会把自机按在线下
  几像素处顶住（护栏实测）。安全分永远压过它：上方被弹幕堵死时冲不上去，限时一到就放弃，
  绝不硬闯。state-2 散射物冲线路过上部时顺路身体接（不参与转化，原版如此）。
- **参数**：勾选「智能道具线」（默认开）、滑条「道具线触发价值」（`poc_min`）；
  CLI `--no-poc` / `--poc-min`。
- **护栏**：`check_plan.py` 用例 29–35（集群抬价压过近距离 / 判据三件边界 / 状态机全流程 /
  冲线权重 500 拉不进死路 / 过冲区替代攻击项 / read_frame 三态分拣 / 散射延迟判干等）；
  `check_autofire.py` 道具线用例 3 项（满火力触发传目标 / 方向朝上 / 火力不满全程不冲）；
  `item_sweep.py` 双组场景：集群版收集 79%（远簇 36/36）vs 对照 26%（远簇 1.2），5 种子平均。

### 3.17 自动进下一关（关卡过渡 + 开场对话）

- **依据**（原版 `Gui.cpp` 的 msg 虚拟机，新典同构）：
  - 关卡结束 → `MSG_OPCODE_STAGEEND` 把 curState 置成 **3（GAMEMANAGER_REINIT）**，
    `GameManager::AddedCallback` 里 `currentStage++` 后**自动**载入下一关 —— **不需要按键**。
    旧版把非关卡画面一律当退出条件，于是每打完一关就停（这正是本次要修的那件事）。
  - 关卡开场的对话是 `MSG_OPCODE_WAIT`：只认 `WAS_PRESSED(TH_BUTTON_SHOOT)`、两次按下沿
    还要隔 ≥8 帧（`Gui.cpp:577`）—— 自动射击是**按住** Z 的，按住永远推不动它，卡在第一句。

### 3.18 玩家让位（人一上手，脚本停手）

- **判据**（`tools/human_watch.py`）：本进程装低级键盘钩子 `WH_KEYBOARD_LL`，只认**非注入**按键 ——
  注入键带 `LLKHF_INJECTED` 位，且 `th06.INJECT_TAG` 写在自己的 `dwExtraInfo` 上，双判据。
  为什么非用钩子：`SendInput` 的键同样进系统键状态表，`GetAsyncKeyState` 分不出人机。
- **让位条件** = 「最近 `human_idle` 秒内有人按键」**或**「此刻仍有人按着键」。只看时间窗不够：
  人一直按着方向键时窗口一过脚本就会把手柄抢回来，而那正是最不该抢的时刻。
- **让位期间**：一个键都不发（含 Z 连射与灵击），方向强制 `none`、`prev` 也归 `none`；
  松键走 `release_all(held, skip=watch.physical())` —— **跳过玩家正按着的键**：
  SendInput 的抬键同样会改系统键状态表，硬松会把人家按住的右方向顶掉。
- **恢复**：人停手 `human_idle` 秒（默认 2s）后自动接管，日志 `▶ 玩家停手`。
  让位期间掉命 / 前台切走仍按原安全闸退出。
- **钩子装不上**：日志 `! 键盘钩子装不上`，让位失效、躲避照跑 —— 不致命。
- **参数**：勾选「玩家操作时让位」（默认开）、滑条「让位静默时长 秒」、CLI `--no-yield` /
  `--human-idle`；自测 `py tools\human_watch.py --seconds 8`。
- **护栏**：`check_autofire.py` 让位用例 4 项（期间零按键、开始即松键、停手后接管、
  玩家按着的键不抬、关掉后不装钩子）。**⚠ 尚未实机验证**（见待办）。

### 3.19 残机 0 仍照常避弹（最后一条命不弃疗）

- **判据**：`curState=2` 且 `Lives=0` → `NO_LIVES`，**可发方向键**。残机是**备用命**，
  0 只表示没有后备，这一局还在打。
- **旧行为错在哪**：`lives == 0` 被当退出条件，脚本一进最后一条命就松键站桩 —— 直接送死。
  当初是为躲 Continue 画面的坑（见 PITFALLS），但闸装错了位置：该防的是 Continue 画面本身。
- **安全靠两道闸，不靠残机数**：
  - `dying` 的判定提到 `Lives==0` **之前**：结算完（`respawn <= 0`）立即松键退出，
    赶在 Continue 出现之前；窗口内（`respawn > 0`）照旧走死亡炸弹抢救。

    暂停（`running=False`）同样排在残机 0 之前。
- **靠开关与出厂默认同源**：CLI 的反向开关是 `--stop-on-death`（掉命即退），
  默认与 `default_params()` 的 `keep_going_on_death=True` 一致；GUI 勾选项「掉命后继续」同义。
- **护栏**：`check_autofire.py` 残机 0 用例 11 项（判据 5 + 主循环 6）。
- **实机验证**：真实残机 0 的局里 `py tools\dodge.py --dry --frames 120`（不按键、不抢前台）

### 3.20 低速模式 focus（只需微调时半速走）

- **触发**：**原地不动的间隙**（`scores['none']`）≥ 安全分数线 + **低速门槛余量**
  （`FOCUS_SLACK`，默认 12px）才按住 Shift 切低速 —— 站着不动都够安全，说明这一步
  不是为了活命，只是微调（对齐输出位 / 捡近处道具 / 离开边界）；必须躲时立刻回高速。
- **为什么看 `none` 而不是「最优方向的间隙」**：后者一片太平就成立 → 自机常年半速
  （实测就是这个表现）。`none` 的间隙与速度无关（不动就没有外推），先查高速那次就够。
- **双速规划**：每帧对快 / 慢两个速度各跑一次 `plan()`，**慢的那次必须自己重规划**。
  为什么：`plan()` 的间隙是按 `speed` 外推轨迹算的 —— 拿高速轨迹去执行低速 =
  以为走得到、实际少走一半。**必死预判也跟着当前速度走**（`doomed_gap(speed=sp_exec)`）。
- **低速 = 精确半速**（反汇编 + 结构常量 4.0 / 2.0，斜向同样归一化）→ `speed × 0.5` 就对，
  不用另标一套 DIRS。依据 → MEMMAP §12。
- **三条例外**：冲线期强制高速（那件事的本质就是快点上去）；已在低速时门槛打折
  （`FOCUS_EXIT = 0.5`，防在门槛上下逐帧横跳）；原地不够安全时根本不跑第二次规划
  （省一半算力，也是要躲时的常态）。
- **顺带收益**：focus 会换射击函数（`Player+0x7720` / `+0x7728` 每帧二选一），
  射击形态跟着收束 —— 不只是变慢。
- **护栏**：`check_autofire.py` 低速用例 8 项（只需微调时按 / 被围住不按 / 必须躲不按 /
  够活但不宽裕不按 / 门槛滑条生效 / 关掉后不按 / 退出时松开 / 冲线期高速）。
- **实机验证**：`py tools\verify_focus.py` —— 只按 Shift、不按方向键（自机不动），
  读输入位图 bit2；附近 60px 内有子弹就拒绝执行。**⚠ 尚未实机跑过**
  （工具就绪时游戏已退出，见待办）。想量低速实际速度：`py tools\calib_speed.py --focus`。

### 3.21 逐弹判定半径（弹幕的判定大小不再一刀切）

- **问题**：原来所有子弹共用 `BULLET_R = 3.0`（威胁距离 `PLAYER_R + BULLET_R = 4.25px`）。
  但判定半径是**每颗子弹自己带的** —— 小玉与最大档差 8 倍。
- **查证链**：反汇编 `Player::CalcKillBoxCollision`（RVA `0x6A980`）的 `minss` + `mulss`
  → 调用点 `0x11418` 的 `lea r8, [rbx+0x5f4]` → 与原版反编译源码
  `ref-th06-decomp/src/BulletManager.cpp` 的 `&curBullet->sprites.grazeSize` 互证。
  公式 `r弹 = min(grazeSize.x, grazeSize.y) × 0.5`（半宽常量 RVA `0x30CD58` 实测 = 0.5）。
- **实测**：本机抓到 4349 颗 4×4（r=2.0）与 1747 颗 6×6（r=3.0）→ 新典**沿用原版分档表**
  （4 / 5 / 6 / 9 / 11 / 16 / 32）。大玉 32×32 → r=16.0，旧算法少算 13px。
- **改法**：`read_bullets()` 多返回一列逐弹半径；`plan()` / `doomed_gap()` 改成
  「先各减各的阈值，再取 `min`」（先取 min 再减常数等于退回旧行为）。`BULLET_R` 退居兜底。
- **附带确证**：`Bullet + 0x618` 是 `isGrazed` —— 判死的**前置门**（必须先擦到才会被击中）。
  全链条 → MEMMAP §3。
- **护栏**：`check_autofire.py` 5 条（同一位置：小玉 +8.75 / 普通 +7.75 / 大玉 −5.25）。

### 3.22 空旷区吸引 + 自动回中（第六关被「磨死」的治法）

- **问题**：第六关符卡里它不被打死，是被**磨死**。实测三次被击中的最优方向间隙都是个位数
  （1.4 / 8.2 / 4.9px），且是被追上的 —— 3 秒内从 `dl=21.1` 掉到 `none=1.7`。
  根因：逐帧挑「当前间隙最大」只是局部最优，密集弹幕里那常常只是**弹与弹之间的一条缝**，
  钻进去越走越窄。
- **两个新软项**（都只在够安全的方向间决胜负，安全判断永不被覆盖）：
  - **空旷区吸引** `clearance_cost()`：问的不是「最近那颗会不会撞上」（那是安全分），
    而是「这一带弹多不多」—— 软化计数（线性核，半径 110px）归一化后当软项。
  - **自动回中** `recenter_cost()`：离场地中心超出 **自由半径 110px** 才牵引，**带内恒 0**。
    它补的是贴边项够不到的地方，主要是**顶部中间**（离四周都不近、贴边项给 0 分，
    但上方弹幕刚生成、反应距离最短）。**不是**旧版那个被否掉的「全局中心吸引」。
- **关键坑（复盘要点）**：第一版给空旷项用了和别的软项一样的 `ATTACK_STEP`（4 帧 = 18px），
  **等于没生效** —— 9 个方向的落点彼此只差几十像素、评价半径却是 110px，各方向空旷度高度相关
  （同帧极差仅 0.20，开/关决策差异率 1.2%）。改用**独立前瞻** `CLEAR_STEP = 12 帧`（≈53px）后
  极差 0.85。前瞻不能更大：20 帧时 38% 的帧会把自机往边界赶。
- **实测标定**（`_tmp/calib_clear.py` / `sweep_clear.py`，FINAL STAGE 符卡真实快照）：
  `CLEAR_R = 110`（计数 p50≈17、max≈31 → `CLEAR_REF = 32` 不饱和）；
  前瞻 12 帧 + 权重 25 时差异率 10%、空旷度 0.199→**0.161**、平均安全分 12.91→**14.37**、
  **最差单帧 0.00px**（零代价；旧 4 帧前瞻是 −11.03px）。
- **实机**：FINAL STAGE 挑战模式长跑 5927 帧 / 102 秒，弹数长期 200~380（峰值 416），
  **炸弹全程未消耗、一次没被击中**（对照：改前的 212 秒跑用掉 5 次灵击）。
- **副作用**：空档期在自由半径内没有梯度也没有阻尼 → 自机在带内来回游走（无危险，仅观感）。
- **护栏**：`check_plan.py` 12 条 —— 前 6 条钉两个函数的单调性与边界，后 4 条在**固化的真实弹幕帧**
  上跑（base64 内嵌，不依赖游戏）：权重拉满时必须选中「最空旷 / 最靠中心」的方向，
  且**绝不选中会中弹的方向**。
- **半径边界（2026-09-24 用户报「空旷区吸引无效」后补）**：`clear_r` 过大不是「更强」而是**退化**。
  实机保存值是 `clear_r = 999`（滑条上限 200，Spinbox 不挡键入）→ 120 帧真实快照实测
  **九向空旷度 100% 完全同值、开/关决策差异率 0.0%**（权重 25 与 100 同样为 0，因为
  软项对每个方向减同一个常数）。半径 200 也不该用：极差只有 0.309，且安全分 10.49→7.70、
  最差单帧 −26.55px。**110px 是本项的标定点**（极差 0.846），要更强就加权重而非半径。
  GUI 已加超范围告警（`dodge_gui.warn_range` + `check_ranges`）；坑 → `01-规范/必读-动手前的坑-PITFALLS.md`。
- **边角倾向（2026-09-24 用户报「开了空旷区就躲角落」后补）**：空旷度只看局部弹密度，
  而弹幕从上往下生成 → **边角天然弹少**，权重越大越往角落退：影子推演实测「终点进角落
  （离边界 < 80px）」关 8% → 权重 25 时 31% → 60 时 42%。**回中与贴边都压不住**
  （回中 25→40 无变化，贴边 42→120 只到 29%，因其只在落点离边界 < 60px 内生效）。
  改法：密度按「圆落在场地内的可用面积」归一（`clear_area_frac`，边角的圆被边界切掉一半），

  细节 → `01-规范/必读-动手前的坑-PITFALLS.md`。

### 3.23 激光几何修正 + 横扫预测 + 敌人运动预测（Laevatein 的根因）

- **症状**：No.123 禁忌「Laevatein」里被高速横扫的激光追上打死；激光修完后仍
  **「撞到敌人身上死亡」**。
- **几何（采样实测 `angle = 90°`）**：激光是**竖线**。`pos` 只是**轴原点**，线段沿 y
  铺满整个场地高度（`pos.y = 48` + `[start, end] = [32, 400]` → 实际 y ∈ [80, 448]）。
  所谓「从左到右扫」= 这条竖线每帧 **+6px 在水平方向平移**。
  → 水平跑不掉（6 > 自机 4.39），唯一出口是**上下走出线段端点** ——
  **而上方那个端点正是蕾米莉亚**（实测 AABB 56×56、y ∈ [52, 108]）。
  这是「撞敌人」的一半原因：出口本身在人身上。
- **三个错误，逐个修**：
  1. **线段少了 `startOffset`**：真值是 `pos + 方向 × [startOffset, endOffset]`，
     旧实现按 `[pos, pos + startLength]` 算。MEMMAP §7.1 有三个字段被误标（已改）。
  2. **轴原点 `pos` 每帧平移**（实测 +6px/帧，比自机还快），**槽里读不到** →
     `LaserMotion` 逐帧差分，`laser_gap(…, lvx, lvy, ts=ts)` 按第 t 帧外推。
  3. **敌人被当成静止的**（本次）← 前瞻里子弹（`vx`/`vy`）、激光（`ts`）都有速度，
     唯独敌人没有，而敌人池**根本没有速度字段**（MEMMAP §6）→ `EnemyMotion` 同款差分。
     实测：不外推时自机把「冲下来的敌人」那格算成 **+120.8px（安全）**，
     外推后同一格是 **−51.2px（必死）** —— 撞机就是这么来的。
- **改法**：`laser_gap()` 三件事各算各的 —— 轴原点平移(`v·t`)、终点偏移(`speed·t`)、
  起点偏移(`max(start, endₜ − len)`，生长阶段起点不动)；`read_frame(motion=…)` 逐帧喂速度；
  读取端换**命名元组**（字段一多，位置解包必然静默错位）。
- **预警期必须特殊处理**：预警期 `pos` 静止、`speed = 0`，**「它会不会扫、往哪扫」
  在预警期没有任何信号** —— 自机按几何算「安全」，于是继续输出，等它开火已经来不及
  （用户原话「激光要出了还在打敌人，而不是立即远离」）→ `WARN_RECT_W` 矩形避让。
  **只能是软项**：它算的是「逃出区间还需多少」，与碰撞间隙不同量纲，混进 `min()`
  会把「撞敌人」盖掉（实测症状：自机为了躲激光径直撞进 BOSS）。
  软项还得有**自己的前瞻**（`WARN_RECT_STEP = 24` 帧）：4 帧的落点分不出区间里的深浅
  （同款坑见 `CLEAR_STEP`）。
- **敌人余量 `ENEMY_MARGIN = 48px`**：`comfort = 1px` 是用户拍板的手感基准（软项闸门），
  于是池内「间隙 1px」与「间隙 25px」只差 `margin_w`（8 分，且被 `MARGIN_CAP` 截断），
  而进攻吸引 55 / 矩形避让 80 都是几十上百 —— 自机会主动选「擦着敌人 1px 过去」。
  子弹擦过去是常态，**敌人擦过去是死亡**，两者不能同一个定价（同 `LASER_MARGIN` 手法）。
  `LASER_HORIZON = 40` 是激光的独立长前瞻，另一块辅助。
- **证据强度（诚实标注）**：`_tmp/laser_trace_*.csv` 的 `screen` 全是
  `MENU` / `CONTINUE` / `NO_LIVES` —— 激光参数是符卡残留的**真实几何**（上面的几何结论
  站得住），但**自机位置同样是残留的**，所以拿它跑 replay 得到的「决策变化」不代表实机；
  `sim_laser_escape.py` 的五段局面同理，只当参考。**实机验收仍未做**（需重开一轮打 No.123）。
- **护栏**：`check_plan.py` 用例 37–43（横扫带时间维、静止对照、生长阶段、轴原点平移、
  差分与槽复用、长前瞻、预警矩形的代价函数与决策、敌人差分与外推、敌人余量）。

### 3.24 子弹运动预测 + 旋转激光（"转向弹 / 旋转激光躲不掉"的根因）

- **症状**：加速弹、转向弹、旋转激光躲不过去 —— 算着安全，弹却自己拐过来 / 扫过来。
- **根因**：两种外推都只有"当前状态的直线"。
  ① 子弹只读 `vx/vy`，不读 `exFlags` —— 而新典**保留着原版整套加速 / 转向机制**；
  ② `LaserMotion` 一见 angle 变化就把该槽速度记 0，`laser_gap()` 的朝向又写死成当前值 ——
  旋转激光等于完全没有运动预测。
- **做法**：
  - `read_bullet_frame()` 一次读取带回运动参数（`exFlags` / 加速度 / 转向参数 / `timer`）；
    旧接口 `read_bullets()` 仍是 6 元组（内部包一层，调用点不动）。
  - `dodge.bullet_paths()` 按原版机制逐帧推进：加速弹抛物线、`0x20` 连续转向、
    `0x40/0x80/0x100` 定时换向（含间隔内的速度线性衰减）。**普通弹仍走一次向量化直线。**
  - `LaserMotion.speeds()` 增差分**角速度**，槽复用判据换成
    「阶段 / 计时倒退 ∪ 位移超阈值 ∪ 角度跳变超阈值」；`laser_gap(..., lom=ω)` 按第 t 帧朝向算线段。
  - `read_frame()` 过滤消散阶段（state 5，无判定）。
- **开销**：300 弹里 200 颗特殊弹、`horizon=16` 时 `bullet_paths` 1.0ms（帧预算 8%）；
  全普通弹走快路径，与旧路径持平（`_tmp/bench_bullet_paths.py`）。
- **护栏**：`check_plan.py` 用例 44–47（+ 用例 39 扩了角速度与阶段倒退判据）。
- **待实机验收**：采样时游戏停在 Continue，**弹幕是冻结残留**（`+0x2C` 的 timer 从不递增），
  战斗里四类各占多少、速度量级如何都还没实测。

### 3.25 "练符卡时一死就再也起不来"的三个停机点（+ 只读观测器）

- **症状**：符卡练习里被击中一次后，避弹再也不动，之后每一局都原地被打死。
- **根因**：三个"误判成非关卡画面 → 松键退出"的点，一次连打三处：
  ① `isInRetryMenu=0xFF` 被判成「Continue 画面」—— **符卡练习失败后的 "Failed..." 菜单同样是 0xFF**
  （依据 `0x6A430` 的 `mov byte [0x549D42],0xff` = 原版 `Player.cpp:247`）；
  ② 按 Z 重试后经过 `curState=12`（新典自加），判成未知场景退出；
  ③ 紧接着 `curState=0`（INIT），同样退出 —— **补完 ② 又在 ③ 上踩**。
- **做法**：
  - `screen_of()`：`0xFF` 判 `CONTINUE`（描述改成"失败菜单"），`curState ∈ {0,12}` 判 `RELOAD`。
  - 主循环：`CONTINUE` 松键、等 `MENU_WAIT` 后按一次 Z（`--resume` / GUI「失败菜单按 Z 继续」开关）；
    `RELOAD` 不按键干等（超 `RELOAD_TIMEOUT` 才退出）。
  - 新增 `tools/watch_live.py`：**只读**观测器（不按键、不切前台），在被打中 / 死亡 / 画面切换时
    打现场 —— 谁碰上的、激光的完整参数、前 N 帧间隙曲线；`--csv` 逐帧落盘。
- **实测**：改完 94 秒连打 10 轮符卡（原来一轮都跑不完）。
- **根因已定位（2026-09-27，死亡黑匣子复盘 19 例）**：**九向全负时候选池被清空 → 软项整体旁路**。
  `plan()` 的 `pool = [n for n, s in scores.items() if s >= max(top - risk, 0.0)]` 里那个 `0.0`：
  `top < 0` 时池直接空掉，只剩 `max(scores)`；而「预警激光马上要开火、得沿轴线往外走」
  **只有软项知道**（`warn_rect_cost`）→ 自机选 `none` 站桩（131730 静止 25 帧被打死；
  123939 静止 **223 帧 / 3.72 秒**）。
  **为什么会全负**：Laevatein 开局 48 条光柱同时瞄准自机生成，每条带 `LASER_MARGIN=16` 的余量
  → 九向没有正分格（作者在 `dodge.py` 218 行已记录同一现象）。
  **修法试过、并被实机证伪（2026-09-27）**：
  ① 病根确认无误 —— `pool` 的 `max(top - risk, 0.0)` 下限在九向全负时把池清空、软项整条旁路；
  ② 按此做的 `warn_pool`（放开池 +「必须有预警线」+「必须未侵入」两个限定）离线很漂亮
  （20 例「选不动」194/260 → 70/260、14 例不再站桩、**0 例反向**），**实机却是错的**：
  135407 那例自机从帧 177 起移动 8 帧、方向**朝 BOSS**（帧 178~185 一路 Δ=(0,−4.0) 到 y=233），
  随后停在 BOSS 正下方，被一颗垂直落下的加速弹打死（真凶：弹槽 60）。
  **为什么**：`warn_rect_cost` 找的「最近出口」在几何上就是**上方** —— 自机 y=233 时到上端点
  （y<80）只 153px、到下端点（y>448）要 215px，而上端点正是 BOSS。设计者本意是
  「软项提议往上、**安全分否决撞 BOSS 那一步**」，但**九向全负时安全分的否决机制本身就失效了**
  —— 站桩（不放宽）与冲 BOSS（放宽）是同一个缺陷的两面。
  **试过无效**：`center_w=0` / `attack_w=55` / `risk=20`（wide 分支不吃 `risk`）/ 关余量项；
  **唯一能让自机往下走的是关掉 `warn_rect_cost` 本身**。
  **现状**：`warn_pool` 默认关，行为与改动前逐字一致（20 例复算两侧都是 194/260）。
  **正路**：把敌人位置喂给 `warn_rect_cost`，让出口选择避开敌人 —— 不是放开 pool。
  **另两条已证无效的路**：`laser_armed`（摘预警线 → 走进即将开火区）、`laser_margin`
  （48 条覆盖全场时每条对九向**同等**扣分，16→0 只平移分数、**排序逐字不变**）。

### 3.27 掉命取证：死亡黑匣子 + 死因解剖（2026-09-27）

- **要回答的问题**：脚本只打一行「掉命」，答不出为什么 —— 连它自己都不知道。
- **`watch_live.py` 为什么不够**（两个硬伤）：
  ① 游戏在自机撞进判定圈那**一帧**判死，`respawnTimer` 走满 8 帧才结算掉命；
     watch_live 在**死亡上升沿**打现场 → 真凶早已飞走，剩下的是路过的无辜弹。
  ② 20fps 抽样对 60fps 的游戏 = 3 帧取 1，**判定那一帧大概率没被采到**。
- **做法**（两个工具一对）：
  - `tools/death_recorder.py`：逐帧把完整世界录进环形缓冲
    （自机 / 全弹含 exFlags 运动参数 / 全激光含轴移转角 / 全敌人盒与发弹倒计时），
    掉命瞬间（`deaths` +1 或 `Lives` 下降或进 DEAD）冻结前 N 帧落盘 npz。**纯只读**。
- **两种启动方式**：
  - **挂进脚本（推荐）**：控制台勾「死亡黑匣子」/ `py tools\dodge.py --blackbox` ——
    `run_session` 新增的 `on_world` 钩子把主循环**已经读到**的世界交给 `BlackBox.feed`，
    只多 3 个小读（focus / 输入位图 / 火力），**不额外占 2MB/帧 带宽**。
    控制台状态栏显示 `● 黑匣子 N 帧·已存 M 例`，落盘时日志出行。
  - **独立跑**：`py tools\death_recorder.py`（自己读帧，约 6ms/帧）——
    适合「脚本单独跑、黑匣子只旁听」；两者同开才会互相抢 CPU。
  - `tools/death_report.py`：读 npz 出四段 ——
    ① 真凶：用**游戏自己的碰撞几何**（弹半径 / 激光线段 / 敌人 AABB vs 自机判定圆）
       扫全部帧，取首个相交帧的那个实体；
    ② 脚本视角：判定帧之前的九向评分 —— 它是「看见了躲不掉」还是「压根没看见」；
    ③ 反事实：从判定帧**之前**逐帧起步试九向，看最早哪一帧还有活路（= 还剩多少反应时间）；
    ④ 结论行 + 「对号入座」该往哪改。
- **决策不在采集端算**：世界已经录下来了，九向评分由 report **离线复算**（同一个 `dodge.plan()`）。
  好处：采集端省 2.7ms/帧、黑匣子职责纯粹、同一段世界可换参数重算
  （`--param clear_w=0` 试「换个参数会不会活」）。
- **实测**：独立跑跟帧 60fps **零漏帧**、单帧 5.8~6.7ms（35%~40% 帧预算）；
  120 帧试样 20 KB（冻结画面的弹幕逐帧相同，压缩率极高）。
- **验证**（`2026-09-27`）：
  - `py tools\verify_blackbox.py` 实机验链路：真读帧 → 人为触发 → 落盘 → 解剖器解析回来，
    **✓ 通过**（字段齐、子弹 21 键、触发原因正确）；
  - 控制台接线用桩替换 `run_session` 冒烟：勾选建实例 / `on_world` 送达 / 未勾选零开销，**✓ 通过**；
  - `check_autofire`（run_session 回归）、`check_plan`、`death_report --self-test` 全过。
- **自测**：`py tools\death_report.py --self-test` —— 合成「弹 vy=6 直线撞静止自机」，
  断言真凶槽位与「首次侵入」定义，**不需游戏**。
- **限制（诚实标注）**：
  - 反事实的世界取记录的真实轨迹；**瞄准弹 / 瞄准激光会因自机改位而改道** →
    「能活」偏乐观；固定弹幕与已发射激光下结论可靠。
  - **独立跑**与躲避脚本同开才会抢 CPU（两边各读约 2MB/帧）；挂进脚本（勾选）不抢。
  - 内嵌模式不单独计时（开销已计在主循环里），报告里那栏显示「内嵌未单独计时」；
    撕裂帧检测只在独立跑时有效（内嵌时主循环与世界读取在同一段里）。
- **实战检验（2026-09-27，18 例）**：`_tmp/death_*.npz`
  - **主根因**（预警阶段激光进安全分 → 站桩）与 17 例批量消融 → §3.25 末段。
  - 其中四例是**被击中后用自动炸弹救回**（`lives` 未减、`bombs` 各减 1、`key` 出现 bit1 按下沿）
    —— 不是掉命，但 bomb 从 4 耗到 0。
  - `113850` 是 36 个杂兵的 `ENEMY_MARGIN=48` 负分圈锁死全场（**未修**）。
  - **已修**：`ESCAPE_RANK` 改按「窗口内还有几帧不在判定圈里」排
    （见 `DO_NOT_REVERT`，护栏用例 48/50）。

    是**整局累计**，别拿它判缓冲质量。
- **复算参数必须与实机一致**（2026-09-27 补）：黑匣子落盘把当时的 cfg 写进 `meta['params']`
  （`BlackBox(params=cfg)`，CLI 与 GUI 都已传）；`death_report` 用 `live_params()` 取
  「meta → `dodge_params.json` → 出厂默认」三级。此前复算走 `plan()` 的函数兜底值，
  与实机差出 horizon 20/30、attack 125/0 —— 报出的「脚本视角」不是脚本当时算的分数。
